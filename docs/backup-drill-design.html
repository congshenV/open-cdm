备份恢复演练 · 设计文档

在任意 RDS 实例上人为触发：用指定备份集克隆实例，确认备份可恢复；克隆完成后对 源实例与克隆实例做数据对比。分期交付：一期只做备份恢复（发起 → 克隆 → Running 判成功 → 人工下线跟踪），数据对比（库级 + 用户选定表的行级校验） 与演练报告（md）二期。全部过程与结果落库。

关联：docs/dmops-design.md（dmops 总体设计）、docs/dmops-integration-design.md（console 代理 / OpenAPI 链路）。 版本：v7 · 2026-11-04 分期定稿（一期备份恢复 / 二期校验报告；v6 为 review 修订稿）

1. 总体流程

用户在实例详情 → 备份详情 Tab → 备份集列表 → 行内「备份恢复」按钮
（可用则点击 → 预览弹窗 → 编辑 → 参数检测 → 启动，见 §2.3）
        │
┌─ cloning ────────────────────────────────────────┐
│ 1. 实例详情接口回填克隆参数（§2.1 映射表）          │
│ 2. 调 CloneDBInstance 创建克隆实例（Postpaid 同规格）│
│ 3. 轮询实例状态至 Running                          │
│ 4. 在 CloudDM 注册克隆实例为数据源（拿 dsId）       │
└──────────────────────────────────────────────────┘
        │
┌─ comparing ──────────────────────────────────────┐
│ 自动对比（所有演练固定执行）：                      │
│   库名集合 + 每库表数量（只记 diff，不判终态）      │
│   每库数据量级（SUM data+index length，仅参考）     │
│ 行级校验（仅用户选定的库-表，逐表执行）：            │
│   选定表须有主键/唯一索引 + 自动更新时间列           │
│   选备份后未变更的行，主键点查克隆实例逐列对比       │
│   最多 10 次尝试，每次尝试独立落库                  │
└──────────────────────────────────────────────────┘
        │
   演练结束（不删实例）
        │
   演练详情 + 导出报告（第一期 md；html / pdf 后续按需开）
   克隆实例由运维同学在阿里云、CloudDM 中人工下线（见 §9）

状态机（ops_backup_drill.status）：

pending → cloning → comparing → success | partial | failed
   ↘ canceled（仅 pending 可取消；CloneDBInstance 请求发出后不可取消）
  • 分期（2026-11-04 定）：一期交付「发起 → 克隆 → Running → 人工下线跟踪」， 数据源注册（§3.3）与数据校验（§4 整章）二期——一期不产生 comparing/partial 状态
  • success：一期 = 克隆实例 Running（§2.2）即成功；二期 = 注册 + 对比 + 行级校验全部通过的完整判定
  • partial（二期出现）：行级校验未全部通过——任一选定表十次尝试全失败， 或选定表全部被跳过（skip/warn）、零张表实际完成校验（零样本记 partial）
  • AUTO 库级/表数量差异（§4.1）只记录、不判定终态：对比口径是 "源当前元数据 vs 克隆（备份时点快照）"，备份后的正常业务变更（建库/删库/建表/删表） 同样产生差异，无法与备份异常区分——报告中如实列出并标注"可能为备份后变更"
  • failed：执行错误——一期为克隆提交失败、轮询硬错误、克隆超时；二期另有注册数据源失败、SQL 连续异常
  • 无清理阶段：演练完成后克隆实例保留，由运维人工下线
  • 进程重启可从当前阶段续跑（状态落库 + 幂等推进，见 §8）

2. 克隆接口与参数映射

克隆接口为 CloneDBInstance；参数来源就是我们现有的实例详情接口 （DescribeDBInstanceAttribute，GET /v1/instances/{id}）+ 备份集列表（DescribeBackups）。

D. 边界决策

  1. 规格/容量/存储类型走默认（不传）：克隆实例是静态快照，同容量必然够用， 且规避"新实例磁盘不能小于源实例"与"规格已下线"两类校验错误； 第一期不提供降配选项，后续要做最小规格克隆再引入规格查询
  2. ZoneIdSlave1/2 不传：阿里云自行调度备可用区；不传备可用区也不触发 "双交换机"约束，保持简单
  3. Serverless 实例克隆已支持（v7 修订，原"第一期直接拦截"决策作废）： 经 CloneDBInstance 官方文档核验，PayType 枚举含 Serverless （MySQL/PostgreSQL/SQL Server 支持，MariaDB 不支持），配合 ServerlessConfig 传 RCU 配置即可。实现口径：源实例 category 以 serverless 开头时 PayType=Serverless + ServerlessConfig 透传源详情返回的 serverless_config（字段名映射：详情 scale_min/scale_max → 请求 min_capacity/max_capacity；auto_pause/switch_force 仅 MySQL，同名透传）； 非 Serverless 源实例不受影响，仍为 Postpaid。Category 两类都不传 （官方文档明确克隆时保持与源一致）
  4. 备份集必须 IsAvail=1 才允许发起（发起入口的可用性判定，见 §2.3）
  5. 增量备份集未验证：BackupType = IncrementalBackup 能否作为 CloneDBInstance 的输入未验证——P1 联调时确认；若不支持，备份集列表对增量备份行禁用 「备份恢复」按钮（tooltip "增量备份暂不支持恢复演练"）

2.2 克隆完成判定

CloneDBInstance 返回 DBInstanceId + OrderId；之后轮询 DescribeDBInstanceAttribute({DBInstanceId}) 至 DBInstanceStatus = Running。

  • 一期：Running 即演练 success（不注册数据源、不做数据校验）
  • clone_instance_id 在克隆提交成功后立即落库——后续无论成功失败都可追溯 （failed 场景的孤儿实例跟踪见 §9）
  • 轮询起点宽容：克隆是异步创建，请求返回后短时间内查不到实例属正常； "实例不存在"等硬错误连续出现（默认 10 次、间隔 30s）才判 failed， 其余状态持续轮询至克隆超时（§8，默认 120 分钟）

2.3 发起入口与交互（备份集列表行内）

入口：备份集列表（实例详情 → 备份详情 Tab → 备份集子 Tab）每行最右侧加 「备份恢复」按钮：

  • IsAvail = 1 → 可点击
  • IsAvail ≠ 1（不可用）→ disabled + tooltip "该备份集不可用"
  • 增量备份集（若联调确认不支持克隆，§2.1-D5）→ disabled + tooltip "增量备份暂不支持恢复演练"
  • 该行已有进行中的演练（未终态）→ disabled + tooltip "该备份集存在进行中的演练"

2.4 任务执行与面板

  • 启动后 dmops 后台 worker 线程（§8）按 §1 状态机推进，发起请求立即返回
  • 简易任务面板：
    • 弹窗关闭后右下角 Toast "演练已启动，编号 DR20261103001"
    • 备份集列表行内按钮位置变为状态徽标（进行中 spinner / 成功 ✓ / 失败 ✗， 悬浮显示当前阶段），点击可打开演练详情
    • 前端 10s 轮询（进行中时）刷新徽标；演练详情页展示分步进度（克隆 → 对比 → 完成） 与耗时
  • 任务终态后徽标定格（克隆完成 ✓ / 失败 ✗）；二期起，成功态行内再出 「演练报告」按钮（点击下载 md 报告，§7），一期无此按钮
  • 取消语义：仅 pending 阶段（CloneDBInstance 请求尚未发出）可取消； 一旦进入 cloning（克隆请求已提交），取消按钮失效——阿里云会把实例创建完， 已进入 cloning 的演练要么走到终态，要么等克隆超时判 failed； canceled 演练不产生克隆实例，不进"待下线"清单

3. SQL 执行通道（不直连数据库）—— 二期

一期不涉及本章（不注册数据源、不执行任何 SQL）；§3.2 数据源匹配、§3.3 复制式注册 随之整体后移二期，一期的 clone 阶段编排在"克隆 Running → 落 clone_instance_id → 终态"处结束。以下为二期定稿内容，保留 v6 review 已核验的结论。

沿用现有链路，console 零改动：

dmops ──POST /api/open/query/syncQuery──► console ──RSocket──► sidecar ──► DB

3.1 dmops 侧封装

app/adapter/clouddm/query.py 提供唯一的 SQL 执行入口：

def execute_query(ds_id: int, env_id: str, database: str, sql: str, timeout: int = 50) -> QueryResult:
    """对指定 CloudDM 数据源执行只读 SQL，返回列定义 + 行数据。

    - AK/SK 签名鉴权（与 CloudDM 专用账号绑定，签名规则同 console OpenAPI：
      AccessKeyId / SignatureMethod / SignatureNonce / Signature，HmacSHA1 + Base64）
    - 请求体（DmApiDsQueryFO）：queryString = sql，queryType = RequestQuery，
      queryForce = False，levels 如下
    - levels = [env_id, ds_id, database]   ← 裸值数字/字符串，不是 'ds:{id}' 前缀格式
      （DmDsConfigServiceImpl.parseLevels：get(0)=envId、get(1)=dsId、get(2)=MySQL 的
      Schema 层即 database；带 'ds:' 前缀会被当作 envId 解析，直接报 DS_NOT_EXIST）
    - env_id 取自 dm_ds.ds_env_id（cdm_ds_repository 查询时一并返回）
    - 硬约束：单条 SQL 必须秒级（syncQuery 服务端 54s future 超时，dmops 侧留 50s）
    - 结果行数上限保护（默认 1000 行，超出截断并标记）——console 侧不保证
      加 LIMIT（仅 SQL 重写开启时才加），截断必须由 dmops 自己实现
    """

签名实现注意：console 的 OpenApiSigner（percentEncode 排序拼接 + HmacSHA1 + Base64） 需要在 Python 侧按字节复刻；SK 是 dmops 侧自行保管的明文（env 配置）， 不要求与 CloudDM 存储的加密格式一致。

对比引擎只依赖该函数，不 import 任何数据库驱动——"不直连实例"的红线保持。

3.2 实例 ↔ CloudDM 数据源映射（已定稿）

核心事实：console 的 syncQuery 执行 SQL 只需要 levels 里的 envId + dsId （["{envId}", "{dsId}", "{database}"]），console 内部完成数据源→sidecar→DB 寻址。 dmops 侧的映射问题因此收敛为一个：拿实例连接地址换 dsId（envId 一并取出）。

实现：直读 CloudDM 的 dm_ds 表（同库，已获准）。

边界例外说明：dmops 与 CloudDM 同库部署。按 dmops/AGENTS.md 安全约束， 经用户逐次确认的场景允许直接操作 CloudDM 的表；本功能即属此类。 访问收在 app/infra/cdm_ds_repository.py，dmops 侧只做按 host 的等值 SELECT。

# app/infra/cdm_ds_repository.py
def find_ds_by_host(host: str) -> dict | None:
    """按连接地址等值查 CloudDM 数据源，返回 {id, ds_env_id, host, instance_desc, status, life_cycle_state}。"""
    # SELECT id, ds_env_id, host, instance_desc, status, life_cycle_state
    # FROM dm_ds WHERE host = :host ORDER BY id LIMIT 1
    # （host 上是 127 前缀普通索引 idx_host，等值查询可用；无唯一键，多行时取 id 最小）

匹配与触发规则（按"实时查 + 缓存"的口径）：

  1. 查询键只用 host（RDS 连接地址是全局唯一域名，port 不参与匹配）
  2. 发起演练 preflight 时实时查一次源实例：命中 → 得到 dsId 并缓存回 ops_resource.cdm_ds_id（列表页展示绑定状态用）；零命中 → 拦截，提示 "该实例未在 CloudDM 录入数据源，请先在 CloudDM 控制台添加"
  3. 缓存字段只在 preflight 命中时回写，不做独立同步任务
  4. 不做手动绑定 UI：dm_ds 表里没有（status 为启用）就引导去 CloudDM 加， 加完重新发起即可（preflight 又是实时查，零延迟生效）

ops_resource 增列 DDL 不变：cdm_ds_id BIGINT NULL、cdm_ds_synced_at DATETIME NULL。

3.3 克隆实例注册为 CloudDM 数据源（已定稿：复制式写入）

克隆实例继承源实例的账号体系（access_key/secret_key 与源数据源一致），注册采用 复制源实例的数据源记录 + 改三个字段的方案，直接写 CloudDM 的表（AGENTS.md 例外规则，已获准）。相比调 console 造一条新配置，整行复制不会漏掉 charset、 driver 等隐藏配置项。

幂等前置：两张表均无唯一键（dm_ds 的 host / instance_id 是普通前缀索引， dm_ds_config_kv_4dm 无唯一键），数据库不防重。插入前先 SELECT id FROM dm_ds WHERE host = :clone_host，已存在则直接复用该 dsId （worker 重启重跑不产生重复数据源）。

dm_ds 主表：复制源行后修改以下字段再 INSERT（真实表 18 列， 含设计早期未列出的 status_message，整行复制策略天然覆盖）

字段 处理
id 不插（AUTO_INCREMENT），拿回新 dsId 落演练记录
gmt_create / gmt_modified NOW()，不复制源时间
host 克隆实例新连接地址（克隆 Running 后 DescribeDBInstanceAttribute 实时取）
instance_id {源instance_id}-drill（辨识用，无唯一约束）
instance_desc {源desc}-drill（用户在发起弹窗可改，即克隆实例名联动）
uid / owner 复制源值
其余全部字段 原样复制（含 access_key / secret_key 密文——克隆继承账号，密文直接拷贝无需明文参与；data_source_type / version / driver / security_type / ds_env_id / bind_cluster_id / status / life_cycle_state…）

dm_ds_config_kv_4dm：按 data_source_id = 源dsId 整批复制到新 dsId

  • config_name = 'host' 的行：config_value 替换为克隆实例新地址 （console 的 syncConf 证明 host 在两张表冗余，只改主表会导致两边不一致）
  • 其余行按 config_name 原样复制。config_name 是 Java 字段名（驼峰）， 注意拼写：连接账号是 userName、口令是 password（isSecret，解密在 console 侧完成）、驱动是 driverVersion（不是 driver）、configVersion 行原值复制（console 兜底缺省为 "1"，带上源值即可）
  • 复制前先检查目标 dsId 是否已有该 batch（幂等场景下查到即跳过）

syncQuery 的数据源授权（已核验，区别于此前口径）：console 的 checkDsAuth 链路会校验调用账号对数据源的授权——owner == 调用者 uid 直接放行， 其次全局授权放行，非 owner 主账号体系直接拒，兜底查授权表（真实相关的表是 dm_auth_res；早期文档引用的 dm_auth_user_auth 是零引用的死表）。 因此 dmops 的 CloudDM 专用 AK 必须绑在具备数据源全局查询授权的账号上 （管理员或已配全局授权的账号），这样 checkDsAuth 第二条直接放行， 克隆出的新数据源（owner 复制源值，可能属于任意主账号）无需任何授权同步。 dmops 不写任何 CloudDM 授权表。

与源实例账号的关系（已定稿：一律复制源账号）：源数据源配置的连接账号 （access_key）在克隆实例上同样有效——克隆继承账号体系；secret_key 是加密态 密文，直读直拷不需要明文。已核验 CryptService（AES/CBC/PKCS5 + 全局固定 key/salt + 密文内嵌 IV，不与行内其他数据绑定）：密文整行拷贝到新行可直接解密， 复制式写入在密码学上成立。发起弹窗不再提供账号/口令输入项，dmops 全程 不接触明文口令。后续若确需演练专用账号，前提是 CryptService 加密算法可移植到 Python 侧生成兼容密文，届时单独评估。

演练结束后克隆实例的数据源保留（配套人工下线流程，不自动注销）。

4. 数据校验设计（核心）—— 二期

一期不涉及本章（无 comparing 阶段、无 steps/diffs 数据）。以下为二期定稿内容。

SQL 只走 information_schema + 主键点查，禁止全表扫描、禁止 COUNT(*)、 禁止任何锁表风险操作；每条 SQL 均须在 54s 内返回。

红线背景：syncQuery 的 54s 超时只杀服务端 future 等待（该链路 JDBC queryTimeout 未设置，超时后 DB 侧语句可能仍在执行），因此对比 SQL 必须 自身高效——游标扫描走主键索引、点查走主键等值，这是设计红线而非优化项。

4.1 自动对比：库级 + 每库表数量（每次演练固定执行）

两侧各执行一次：

SELECT table_schema                       AS db_name,
       COUNT(*)                           AS table_count,
       SUM(data_length + index_length)    AS data_bytes
FROM information_schema.tables
WHERE table_schema NOT IN ('mysql','sys','information_schema','performance_schema','__recycle_bin__')
GROUP BY table_schema

对比规则：

项 判定
库名集合 双向 diff，缺失/多余都记 diff
每库表数量 不等记 diff
每库 data_bytes 近似值，只记录供报告参考，不判定

AUTO 层所有 diff 只记录、不判定终态（§1 partial 语义）：对比口径是 "源实例当前元数据 vs 克隆实例（备份时点快照）"，备份完成后的正常业务变更 同样产生差异，与备份异常无法区分。diff 落库时在 note 标注 "可能为备份后变更"；终态结论只由行级校验（稳定行逐列对比）判定。

不做自动的表名集合 diff 与行数对比（对比简化决策）：表数量大时元数据扫描耗时 且对原实例有影响；行数用 COUNT(*) 明确排除。表名/行级层面的核对收敛到用户选定的表。

4.2 行级校验（仅用户选定的库-表，逐表执行）

发起演练时用户在前端选定要校验的 db.table（可多选，默认最多 5 张）。 选定表须满足：

  1. 有主键或唯一索引（否则无法点查且行无稳定标识，该表记 skip 并说明原因）
  2. 有自动更新时间列：information_schema.columns.extra 含 on update CURRENT_TIMESTAMP——该列是"行在备份后被改过"的判定依据， 必须确认是自动更新；手动维护的时间列不可信，只能作为降级候选 （标记 warning，不进判定）。无自动更新列的表记 warn，按"仅点查不校验稳定性"降级或跳过（可配）

元数据 SQL：

-- 主键列
SELECT column_name FROM information_schema.key_column_usage
WHERE table_schema = ? AND table_name = ? AND constraint_name = 'PRIMARY'
ORDER BY ordinal_position;

-- 唯一索引
SELECT index_name, COUNT(*) FROM information_schema.statistics
WHERE table_schema = ? AND table_name = ? AND non_unique = 0
GROUP BY index_name;

-- 自动更新列
SELECT column_name, data_type FROM information_schema.columns
WHERE table_schema = ? AND table_name = ?
  AND extra LIKE '%on update CURRENT_TIMESTAMP%';

4.2.1 稳定行选择（关键）

选"备份开始前就存在、且备份开始后再没改过"的行，这样该行内容必然来自备份快照本身， 对比才有意义：

  • 阈值用 backup_start_time（所选备份集的 BackupStartTime）而不是 EndTime： 备份窗口内（Start ~ End 之间）被修改的行，其 update_time 仍可能 <= EndTime， 按 End 判会把这类行误认为稳定行——该行源侧当前值与快照值必然不同， 是确定的假 diff 来源。用 Start 做保守排除，代价只是候选行变少 （50 批 × 100 行找一行，通常够用），换来零误判
  • 时区口径（必须处理）：BackupStartTime 是阿里云返回的 UTC 时间，而 行内 update_time 列的字面量取决于实例会话时区（常见 +08），两侧口径 不一致会差 8 小时——保守阈值会反向失效（把备份后改过的行误判为稳定行）。 对比开始前在两侧各执行一次：
SELECT NOW(6) AS session_now, UTC_TIMESTAMP(6) AS utc_now;

用 session_now - utc_now 得到该实例会话相对 UTC 的偏移，把 backup_start_time 折算到与 update_time 相同的会话时区字面量后再比较； 两实例偏移不同时按各自实例的偏移分别折算

  • 在源实例按主键顺序游标推进（每批 100 行，最多 50 批），找到第一条满足 update_time <= backup_start_time(折算后) 的行：
-- 按主键游标推进，避免依赖 update_time 索引导致全表扫描。
-- 游标扫描只取主键列和更新时间列，控制传输量；命中稳定行后再对全列做点查。
SELECT <pk_cols>, <update_col> FROM `db`.`t`
WHERE <pk_cursor_condition>          -- 上批最后一行的主键之后
ORDER BY <pk_cols> LIMIT 100;
-- 应用侧过滤 update_time <= backup_start_time
  • 命中稳定行后，源侧同样按主键点查全列（与克隆侧点查对称）： SELECT * FROM db.t WHERE <pk = ?>
  • 主键序走索引，每批 100 行代价极低，对原实例无压力
  • 若 50 批内找不到稳定行（说明头部数据全是活跃更新的），该表记 no_stable_row，不算失败，记 warning

4.2.2 行对比与重试

克隆侧按主键点查同一行：

SELECT * FROM `db`.`t` WHERE <pk = ?>

逐列对比源/克隆两行：

  • 类型规整：datetime/timestamp 统一格式；float/double 容差比较（相对误差 1e-9）； blob/binary 转 hex；NULL 相等；JSON 规范化后比较
  • 差异列逐列记录（列名、源值、克隆值，默认脱敏为 hash 摘要 + 差异标记，导出报告时不落明文，可配）
  • 源侧行已被删除（点查不到）→ 记 row_deleted_in_source，本次尝试失败，重试时重新选行

重试机制（最多 10 次，任一次全列一致即通过）：

触发重试的情况 说明
克隆实例刚就绪数据未完全可见 克隆 Running 后短暂窗口内点查可能异常
sidecar 会话/网络抖动 瞬时错误
源侧选行失败 换行重选
  • 每次尝试独立落库：attempt_no、状态（pass/fail/skipped）、耗时、失败原因、 对比列数、差异列摘要——报告里十次尝试全部可见
  • 重试间隔默认 30s（可配）；10 次全失败 → 该表记 fail，进 partial
  • 判定为 pass 的数据：源行主键值、克隆行逐列一致（至少 1 个非主键列真实比对过）
  • 零样本：用户选了表但全部被跳过（无主键 skip / 无稳定行 warn 等）， 零张表实际完成校验——"有校验意图但零实际样本"，终态记 partial 而非 success， 报告差异摘要写明"选定表均未完成校验（原因：…）"；审计口径上"没测过"不应绿灯

-- 步骤表：自动对比一条 + 每张选定表各一张（二期才有数据，表随一期 DDL 一并预建）
-- target/差异表 target 长度：MySQL 标识符最长各 64 字符，'db.table' 极限 129，

-- 对比明细表：库级 diff + 行级每次尝试
CREATE TABLE ops_backup_drill_diff (

  clone_value  TEXT        NULL COMMENT '克隆侧值（行级为脱敏摘要）',
  note        TEXT         NULL COMMENT '失败原因 / 差异说明',
  created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,

-- ops_resource 增列（CloudDM 数据源关联；二期 preflight 回写用）。

8. 执行器与并发

  • 部署形态（对照现网部署修订）：dmops 容器 gunicorn 由 -w 4 改为 -w 1（-k gthread --threads 4 保留）——dmops 是 IO 代理型负载 （阿里云 API 长请求靠线程并发），单进程多线程足够；后台 worker 线程挂在 create_app()（此时全进程仅一份），避免多进程重复扫描与"全局并发=1"的跨进程竞态。 启动脚本 package/docker/dmops.Dockerfile CMD 同步修改
  • worker 为全新组件（dmops 此前无任何后台任务先例）：单线程轮询循环 + DB 任务表，不引入工作流引擎：
    • 扫描 status IN (pending, cloning, comparing) 的记录， SELECT ... FOR UPDATE SKIP LOCKED 抢占
    • 每阶段完成后落库再进下一阶段；克隆轮询中每分钟落一次心跳（updated_at）， 心跳超时（10 分钟）的记录可被重新抢占——进程崩溃续跑靠这套心跳， 不存在长时间卡死路径
  • 全局并发演练数默认 1（可配）；同一实例存在未终态演练时禁止新发起 （发起时校验，与心跳超时无关）
  • 克隆超时默认 120 分钟（大库克隆耗时可达小时级，2026-11-04 确认够用）； 对比阶段超时 60 分钟（二期）

配置清单（env 前缀 DMOPS_DRILL_，进 app/config.py 新增 Drill 段）：

配置 默认 说明
DMOPS_DRILL_MAX_CONCURRENCY 1 全局并发演练数
DMOPS_DRILL_MAX_TABLES 5 选定表数量上限（参数检测用）
DMOPS_DRILL_CLONE_TIMEOUT_MIN 120 克隆阶段超时（分钟）
DMOPS_DRILL_COMPARE_TIMEOUT_MIN 60 对比阶段超时（分钟）
DMOPS_DRILL_ROW_ATTEMPTS 10 行级校验每表最大尝试次数
DMOPS_DRILL_ROW_RETRY_INTERVAL_SEC 30 行级重试间隔（秒）

DMOPS_DRILL_SCAN_MAX_BATCHES 50 稳定行游标扫描最大批数

9. 安全与成本护栏

  • SQL 只读白名单：对比引擎无法执行写语句（模板固定 + queryForce=false 两层保险）
  • 无凭据流转：连接账号沿用源数据源（密文整行拷贝，dmops 侧全程不接触明文口令， 见 §3.3）——发起弹窗不再有账号/口令输入项
  • 克隆实例不做自动删除（明确决策）：
    • 演练结束 = 演练流程结束，克隆实例保留（一期的克隆实例为阿里云侧独立资源， CloudDM 数据源二期注册时才产生）
    • 下线由运维同学人工执行：阿里云控制台释放实例（+ 二期起 CloudDM 删除数据源）
    • 待下线清单：详情页固定展示克隆实例 ID（二期加数据源 ID）；列表页 "未下线"过滤 + 逐条"确认下线"按钮（confirm-offline API，置 offline_status=1 并记操作人/时间，便于跟踪遗漏）
    • failed 演练同样跟踪：克隆请求已发出（clone_instance_id 已落库）即进 待下线清单——阿里云不会因演练判 failed 而停止创建，该实例可能稍后 Running 并持续计费；只有 pending 被取消（canceled）不产生实例、不进清单
    • 按量计费实例保留期间持续计费——发起页明确提示，靠"未下线"标记防遗忘
  • RAM 权限（已按 §2 克隆链路确定）：阿里云侧需 rds:CloneDBInstance + rds:DescribeDBInstanceAttribute + rds:DescribeBackups（后两个现有同步 链路已在用，确认 AK 已含；仅 CloneDBInstance 通常需新增授权）
  • CloudDM 侧 AK 授权（二期，随 syncQuery 一并准备）：dmops 的 CloudDM 专用 AK 绑在具备数据源全局查询授权的账号上（§3.3 已核验的 checkDsAuth 链路决定）， 在 CloudDM 界面一次性配置
  • 克隆实例网络白名单（二期联调确认项）：克隆实例的 IP 白名单不保证继承源实例， 一期无数据面访问不受影响；二期注册数据源前需确认 sidecar→克隆库连通， 必要时在阿里云侧补白名单（运维人工操作，进下线前清单）
  • 审计：发起/取消/确认下线（一期）；导出报告（二期）均记录操作人
